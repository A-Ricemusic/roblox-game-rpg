01 / Vision

The first playable slice

The player spawns with a visible starter sword, approaches a hostile training enemy, trades attacks, takes damage, defeats it, and sees it respawn. This thin slice proves every major boundary before the RPG grows around it.

01

Spawn equipped

The weapon model is attached directly to the character. No Backpack item or default Tool grip is involved.

02

Fight responsively

Clicks or controller input trigger a three-hit light combo with custom timing and animations.

03

Face danger

A simple enemy detects, pursues, telegraphs, attacks, takes damage, dies, and respawns.

04

Stay extensible

All damage passes through one service so future buffs, armor, healing, effects, and quests can hook in cleanly.

Scope boundary: phase one supports PvE only. Player-versus-player damage, inventory persistence, loot drops, quests, magic, healing consumables, and finished art are deliberately deferred.
02 / Combat rules

Simple rules, strong feel

Good early combat needs a small number of reliable rules. The system should favor readable timing and positioning over click speed.

Recommended MVP rules

  • Three light attacks chained within a short combo window.
  • Each attack has wind-up, active, and recovery frames.
  • One target can be damaged only once per swing.
  • Attacking briefly limits movement and rotation.
  • Taking a solid hit causes a short, non-chainable stagger.
  • Death disables combat until the character respawns.

Combat state machine

Both clients and the server reason about named states rather than loose booleans. The server owns the authoritative state.

Idle / MovingMay begin an attack.
Wind-upAnimation begins; no damage yet.
ActiveServer samples the hit volume.
RecoveryCannot immediately attack again.
Idle or Next ComboReturn or consume queued input.
03 / Weapon design

Weapons are data, models, and movesets

A weapon is not a Roblox Tool. It is a cosmetic model attached to the avatar plus a shared definition describing attacks. This prevents built-in equip behavior from dictating the presentation.

How the weapon appears

  • On character spawn, the client asks the equipment controller to show the current weapon.
  • A cloned visual model is attached to the right hand with a configured Motor6D.
  • An optional sheathed copy can attach to the back or hip while combat is disabled.
  • Weapon collision stays off; invisible spatial queries determine gameplay hits.

Animation recommendation

Author custom R15 animations in Roblox Studio and reference their asset IDs in each moveset. Set combat tracks to Action priority so they cleanly override locomotion only while needed.

Animation markers such as HitStart, HitStop, and ComboOpen drive local presentation. The server still uses configured timings, so an exploiter cannot move a marker to create extra hits.

Mouse & keyboard

Left click: light attack. Future bindings: right click guard, Q dodge, R skill.

Gamepad

Right trigger: light attack. Future bindings: left trigger guard, B dodge, bumper skill.

Touch

A large attack button near the right thumb. The input layer sends the same abstract LightAttack action.

No hard target lock is required for the MVP. Hits use the weapon’s forward arc and distance, allowing the player to aim naturally with movement and facing. A soft-lock or target-lock camera can be added later without changing damage resolution.
05 / Enemy AI

Enemies should announce intent

The first enemy is a server-controlled training bandit. Its behavior is intentionally predictable so we can tune responsiveness and teach the player the combat language.

IdleWait at spawn and scan periodically.
ChasePath toward the nearest valid player in aggro range.
TelegraphStop, face target, and visibly wind up.
AttackValidate target distance and apply one hit.
RecoverPause before chasing or attacking again.

Safety and performance rules

  • AI logic and damage decisions run on the server.
  • Targets must be alive, targetable, and inside the enemy’s leash area.
  • Pathfinding recalculates on a budget, not every frame.
  • Line of sight is checked before beginning an attack.
  • Attack damage is canceled if the enemy dies or is hard-staggered first.
  • NPC connections and temporary objects are cleaned up on death.

Client controllers

Own input, custom animation playback, weapon visuals, camera shake, sounds, trails, and predicted swing feedback. They request actions but never decide damage.

Server services

Own combat state, cooldowns, validation, spatial hit queries, health changes, enemy brains, deaths, and respawns.

Shared modules

Contain frozen definitions, types, constants, and pure hitbox math used by both sides. Shared code never trusts client-supplied outcomes.

Roblox Studio organization: weapon visuals can live in ReplicatedStorage/Assets/Weapons, enemy templates in ServerStorage/Enemies, enemy spawn markers in Workspace/EnemySpawns, and remotes in ReplicatedStorage/Remotes. The project mapping can be expanded when implementation begins.

Remote requests

RequestAttack(attackType, sequenceNumber) is the only client-to-server combat action needed for the first slice. The client does not send a target, damage number, hit position, or combo index.

Server broadcasts

CombatEvent(eventType, payload) tells nearby clients about confirmed hits, blocks, reactions, and deaths. Payloads contain presentation facts, not trusted instructions.

08 / Validation

Assume every request can lie

Responsiveness belongs on the client; authority belongs on the server. Validation is part of the combat design, not a later hardening pass.

A

Rate and sequence

Reject requests that arrive faster than the equipped moveset permits, repeat a sequence number, or skip impossible state transitions.

B

Server geometry

Build overlap queries from the server-known character position, facing, weapon, and attack step. Never accept a target chosen by the client.

C

Target filters

Exclude the attacker, allies, dead characters, non-combatants, repeat hits, and targets outside the configured attack volume.

09 / Delivery plan

Build in testable layers

Each phase leaves the game in a playable state and closes a particular technical risk before visual polish begins.

1

Foundation and equipment

Create definitions, networking, combat states, the starter sword visual, hand attachment, spawn equip behavior, and placeholder custom animation hooks.

2

Player attacks

Add abstract input, combo buffering, animation playback, server timing validation, spatial hit queries, damage, death, and basic feedback.

3

Enemy loop

Add a training bandit template, spawn markers, target selection, pursuit, telegraph, attack, stagger, death, leash, and respawn.

4

Feel and resilience

Tune timings, add trails/sounds/hit flashes, test latency, handle rapid respawns, clean resources, and profile several simultaneous enemies.

5

Expansion hooks

Expose damage events for quests and XP; add modifier slots for armor, buffs, healing, status effects, critical hits, and elemental reactions without implementing them yet.

10 / Acceptance

Definition of done

The first combat slice is ready when these behaviors work in both solo testing and a two-player Studio server.

Functional checklist

  • Every spawned player visibly carries the starter sword without a Tool.
  • Light attack input produces a reliable three-step combo.
  • Only enemies inside the active hit volume take damage.
  • An enemy can detect, chase, attack, damage, kill, disengage, and respawn.
  • Players can damage and kill the enemy; dead actors cannot attack.
  • Two players can fight one enemy without double-hit or ownership bugs.

Quality checklist

  • No default Tool equip or swing animation appears.
  • Attacks feel immediate at typical simulated latency.
  • Spam requests cannot bypass recovery or deal extra hits.
  • Enemy attacks have visible wind-up and fair range.
  • Respawning repeatedly does not duplicate weapons, inputs, or events.
  • Combat constants can be tuned without rewriting service logic.
Review decisions

Choices to confirm before coding

The plan can proceed with the recommended defaults below. These are the few creative choices that materially affect the first implementation.

Camera style

Recommended: normal third-person camera for the MVP, with optional soft targeting later.

Defense move

Recommended: launch light attacks first, then add a short directional dodge before blocking or parrying.

Character rig

Recommended: standard R15 avatars, which give enough joints for expressive custom combat animations.
